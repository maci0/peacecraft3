# 004 — MDX models

Status: container **resolved**, and now the whole of it. Every model the archives
ship parses: **3,234 / 3,234** on 1.28c, **3,249 / 3,249** on 1.29b, all at MDX
version 800. Decoded: `MODL`, `SEQS`, `TEXS`, `GEOS` (envelope, sub-blocks *and*
the trailer that carries `materialId`), `BONE`, `MTLS`, `GEOA`, `PIVT`, the node
chunks, `TXAN` / `RIBB` / `PREM` / `PRE2` / `CAMS` / `LITE` / `CLID`.

**No chunk's framing is open.** What remains is a short list of *semantics that
were refused* — `PRE2`'s 171-byte prelude and `CLID`'s collision floats — where
the width is proved and the meaning is not, and the bytes are kept raw rather
than guessed. See *Still open — semantics, not framing* at the end.

## The plan was wrong about the format

`PLAN.md` and `TRACKER.md` assumed the old chunked `.mdl` — `VERS` / `MODL` /
`SEQS` / `TEXS` / `PINS` ASCII chunks. **1.28c ships no `.mdl` at all.** The
archives contain 3,234 `.mdx` files and zero `.mdl`. There is no `PINS` chunk
either; the particle chunk is `PREM`. Those assumptions came from the classic
format and were never checked against the installed assets.

## Container

```text
0x0000  "MDLX"
0x0004  "VERS"  4        -> version = 800
0x0010  "MODL"  372
0x018c  "SEQS"  1716
...
```

Each chunk is `tag[4] + u32 payload_size + payload`, starting at offset 4. There
is no chunk count and no index. The only way to parse the file is to walk it and
require the walk to land exactly on the end — which is what makes the layout
trustworthy, and it is asserted for every shipped model on both builds.

An unknown tag is a hard error rather than a skip, so a chunk this build does
not understand cannot be passed over unnoticed. That policy found three tags the
first draft missed.

### The framing is not one framing

`GEOS`, `MTLS` and most other chunks are runs of self-inclusive record sizes, and
that is the shape a shared reader wants. Five families break it, and each broke a
real reader here:

- `HELP`, `ATCH` share `BONE`'s framing — one self-inclusive size covering node
  plus tracks plus an 8-byte trailer.
- `EVTS` measures the **node header only**; its `KEVT` track trails it, outside
  the measured region. `CLID` looks like `EVTS` and is not: its size word covers
  the header **and** the node's animation, and only the geometry sits outside.
  The same size word read the same way is right in 94% of records and wrong in
  the rest — see *`CLID`*.
- `RIBB`, `PREM`, `PRE2`, `LITE` open with **two** sizes: the record's own, then
  the node's — and the node's absorbs the node animation. Their own fields begin
  at `+4 + node_size`, not at a fixed offset.
- `CAMS` has **no node header at all**: the name is at `+4`, and where
  `objectId` / `parentId` / `flags` sit for every other node chunk is the eye
  position. See the gotcha below.
- `TXAN` is a run of records with no node header, addressed by the texture layer
  that names them.

A wrong choice in this table does not usually fail loudly. It produces a walk
that lands on the end of the record with the fields a few bytes off, which
renders something plausible. That is the failure mode this whole note is written
against, so every relation below is stated as an equality the sweep enforces.

### Chunk tags

`VERS` `MODL` `SEQS` `GLBS` `MTLS` `TEXS` `TXAN` `GEOS` `GEOA` `BONE` `LITE`
`HELP` `ATCH` `PIVT` `PRE2` `EVTS` `CLID` `CAMS` `RIBB` `PREM`

Two of these were misread at first from a byte dump: `RIBB` looked like `BIBB`
and `TXAN` like `TWAN`, because the report printed `[82, 73, 66, 66]` rather
than the ASCII. Reading the actual chunk walk settled both.

Tags appear and disappear per model — **249** distinct chunk-set combinations
across the 1.28c set, the same figure whether the tags are read in file order or
as an unordered set — so every chunk is optional. All 20 tags appear in at least
one shipped model; the rarest, `PREM`, is 29 of 3,234.

## `MODL` — 372 bytes

```text
+0x000  char name[]    NUL-terminated, inline
+0x154  f32  0 in 1,742 models, non-zero in 1,492 — meaning unproven
+0x158  f32[3]  minimum_extent
+0x164  f32[3]  maximum_extent
+0x170  u32  150 in 3,227 of the 3,234 records
```

Strings are inline NUL-terminated, not an offset table. The extents scale
sensibly — a footman is ~186 units tall, a town hall ~871.

The trailing word is *almost* constant: 150 in 3,227 records, 0 in five of them
(the `Tornado` family and `MainMenu3d_exp`), 300 in `SeaElemental.mdx` and 210 in
`HeroMoonPriestess_Portrait.mdx`. Nothing is derived from it.

Everything from the end of the inline name to the extents is zero except one
word. At `+0x154`, the last four bytes before `minimumExtent`, sits an `f32` that
reads 0 in 1,742 models and non-zero in 1,492: `MonsoonBoltTarget.mdx` reads
1607.33 against extents of ±1607, `RainOfFireTarget.mdx` 641.9. It sits below the
bounding diagonal in 1,487 of the 1,492, so it is in the family of a radius or a
scale, but nothing in the shipped bytes proves which and nothing here reads it.

## `SEQS` — 132-byte records

```text
+0x00  char name[80]
+0x50  u32  interval_start   milliseconds
+0x54  u32  interval_end
+0x58  f32  move_speed
+0x5c  u32  non_looping
+0x60  u32  0, then 4.0 / 3.0 / 6.0 on some sequences
+0x68  f32[7]  unclassified
```

The stride is derived, not guessed: `1716 / 132` is exactly the footman's 13
sequences, `1584 / 132` the knight's 12, `660 / 132` the portrait's 5. A wrong
stride cannot divide all three by whole numbers.

The values are self-checking: `Stand - 1` runs 167→1667 ms, the knight's
`Walk` carries a ground speed of 380, and attacks set the non-looping flag
while stands do not.

## `TEXS` — 268-byte records

```text
+0x000  u32  unclassified
+0x004  char path[260]
+0x108  u32  0
```

`804 / 268` is the footman's 3 entries, `1072 / 268` the knight's 4,
`4288 / 268` the town hall's 16.

The leading `u32` was first taken for a replaceable-texture id. **That is
wrong**, and the data says so plainly: the town hall has thirteen records with
the value 0. It is reported as `slot` and nothing is derived from it. Paths may
be empty, which is legal.

## Anomalies in Blizzard's own shipped assets

The sweep records **51 on 1.28c and 50 on 1.29b** and reports them without
failing, because they are properties of the shipped assets rather than parser
bugs. Most are unnamed sequences and out-of-order sequence timelines. Four are
worth calling out.

**An un-shipped asset left in the retail build.** `HeroBloodSphere.MDX`, in both
the Hero Blood Elf and Kael model sets, references textures by absolute
developer path:

```text
\\guldan\drive1\projects\War3\ArtInProgress\SharedMaps\Allen\fx\Clouds8x8.tga
```

`ArtInProgress` is the working state, `guldan` is the artist's machine, and the
files are `.tga` rather than the `.blp` everything else uses. The model still
loads in-game, so those slots must not be required for the effect to appear.

**Negative sequence start times.** `ThunderclapCaster.mdx` and
`HeroFarSeer.mdx` both contain a sequence named `nothing` whose start reads
`0xFFFFFC10` — −1008 — followed by a normal end time. A handful more models ship
with unnamed sequences.

**Negative camera key frames.** The only chunk in the format that ships one is
`CAMS`. Across both builds there are **15 tracks / 21 individual keys** per build,
30 / 42 in total, in 9 models per build, and the only two values that occur are
**−33** and **−167**. They are camera tracks in the cinematic-camera families —
`Objects\CinematicCameras\CameraCloseUp*.mdx` on `Camera02`, and
`UI\Glues\SinglePlayer\NightElfCampaign3D`, `NightElf_Exp` and
`UndeadCampaign3D` on `Camera01`, where all three of `KCRL`, `KCTR` and `KTTR`
open below zero. Reading the frame as a `u32` yields a huge number instead, which
is why this is a separate anomaly from "keys out of order" — the two are counted
apart and both are reported without failing.

**Negative frames in `PRE2` too.** 22 of its sub-chunks across both builds open
below zero, the first a `KP2E` at −100 in `Hydralisk`. This is the same
phenomenon as the camera case and is counted apart for the same reason: the
`PRE2` framing sweep treats a negative leading frame as data and an
out-of-order track as a failure, because those are different claims and only one
of them is a parser bug. See *`PRE2`*.

These are data facts, not parser bugs, so they are surfaced as anomalies while
only the real invariants (clean walk, exact strides, the framing equalities
above) are asserted.

## `GEOS` — geosets

The chunk is a flat list of entries, each a **self-inclusive** size — the `u32`
counts its own four bytes — followed by that many bytes less four:

```text
+0x0000  u32 17335   geoset 0 (the body)
+0x0004  "VRTX" ...
+0x43b7  u32  2514   geoset 1
+0x43bb  "VRTX" ...
+0x4d89  u32  1492   geoset 2
+0x4d8d  "VRTX" ...
+0x535d  u32   754   geoset 3
+0x564f  u32  2335   geoset 4
         end = 24430, exactly the chunk length
```

Five geosets for a footman is what you would expect — body, and the pieces that
swap with equipment. The walk consuming the chunk to the byte is what makes the
reading safe; a wrong interpretation cannot land on the final byte. This holds
for all 3,234 models of 1.28c and all 3,249 of 1.29b.

Every sub-block is `tag[4] + u32 count + body`, and the per-tag body width is
fixed. The walk from the first block to the last tiles the geoset exactly.

| tag | body width | contents |
| --- | --- | --- |
| `VRTX` | `count * 12` | positions, three little-endian `f32` |
| `NRMS` | `count * 12` | normals, three little-endian `f32` |
| `PTYP` | `4` | primitive type (a single `u32`, **not** `count` entries) |
| `PCNT` | `4` | index count (a single `u32`) |
| `PVTX` | `count * 2` | triangle indices, `u16` |
| `GNDX` | `count * 1` | vertex group index per vertex |
| `MTGC` | `count * 4` | matrix group id per triangle |
| `MATS` | `count * 4` | bone indices, then a trailer — see below |
| `UVAS` | `0` | no body of its own |
| `UVBS` | `count * 8` | texture coordinates, two little-endian `f32` (u, v) |

Two of these are easy to get wrong and both were got wrong here first:

- `PTYP` and `PCNT` carry **one** `u32` each, not `count` entries. Reading them
  as `count`-sized arrays desynchronises every block after them.
- `UVAS` has **no** body — it is a tag and a count and nothing else, with
  `UVBS` following immediately.

`MDLGEOSETSECTION` from Blizzard's own symbols names the contents `vertices`,
`normals`, `texCoords`, `primitives`, `materialId`. Those names were adopted
**after** the on-disk order above had been measured against vanilla 1.28c bytes.

Checks that make this trustworthy:

- `NRMS` entries are unit length to five decimals across every model, which is
  what a packed or scaled normal encoding would break.
- `PVTX` indices are all `< VRTX` count, for every model in the set.
- The measured vertex bounding box fits inside the model extents.

### `MATS` is decoded, and so is what followed it

The old reading of `MATS` — "the count is the number of groups, so the body width
cannot be derived from it; scan to the next known tag" — was right that the
groups do not describe the span, and wrong that this forced a scan. The count is
exactly the number of node indices, so the body is `count * 4` bytes and nothing
more. The scan-it path left the reader with a span that was **not** all matrix
indices, and the trailer it swallowed is where the geoset's material lives. See
*Geoset→material* below; the framing is proved there and the detail is not
repeated here.

What the sweep asserts, over every geoset of both builds — **17,442** of them:

- the `MATS` body is exactly `count * 4` bytes of node indices,
- `Mesh::matrix_span_u32s` — derived from the count, never scanned — holds that
  width and equals the count the block declares. It measures the node-index
  region *only*; the trailer is parsed from where the span ends, not out of it, so
  the two cannot be confused and a framing error in one cannot be absorbed by the
  other,
- the groups trim into it: `matrix_span_u32s >= sum(MTGC)` always. On 1.28c the
  two are equal in 6,907 of 8,672 geosets and the groups fall short in 1,765 of
  them; never once is the sum the larger. The trim is what keeps that tail out of
  the skinning table, and the span is what lets a caller check the trim rather
  than trust it.

Everything past the `count` indices is the trailer, and the trailer is where the
geoset's material, its bounds and its per-sequence bounds live.

## `BONE` — decoded, and it was variable-length

It was open for a while, and the reason was real: the records are
**variable-length**, which is measured, not suspected. Name offsets in the
footman's chunk step by 104 bytes between most bones but by 52, 156, 212, 360
and 572 elsewhere, so records carry influence lists of differing sizes. The
footman chunk is 4,768 bytes, not a whole multiple of any fixed stride.

What resolves it is not a stride but a relation: the leading `u32` is the record
size **excluding** an 8-byte trailer, so the span is `size + 8` and the animation
tracks occupy everything from just past the node fields to that trailer. The walk
must land exactly on it, which is what makes the reading safe — and it lands
exactly on all **35,257** records of 1.29b and all **35,097** of 1.28c.

```text
+0    u32  size of the record *before* the 8-byte trailer
+4    char name[80]
+84   u32  object id
+88   i32  parent id        (-1 on the root)
+92   u32  flags            (bit 0x100 set on every shipped record)
+96   tracks, ending at +size
+size i32  geoset id        (-1 when unbound)
+size i32  geoset anim id
```

A track is `magic[4] + count + interp + globalSeq` followed by `count` keys, and
the key width comes from the track kind — `KGTR` a vector, `KGRT` a quaternion,
`KGSC` a scalar — with a tangented key appending in and out tangents the same
width as the value. The three mistakes first made in `GEOA` (the wrong-grouped
key sizes, the track header read as 12 bytes, and `len` compared against instead
of `len - 4`) were all made here first and are recorded under *GEOA* below.

`geoset_id` and `geoset_anim_id` are the `MDLBONESECTION` fields. `geoset_id` is
what binds a bone to the geoset it drives, and it is what lets a pose be applied
per mesh rather than model-wide.

## Verification

```text
cargo test -p pcx-mdl                    # container, timeline, texture slots
cargo test -p pcx-mdl -- --ignored       # all shipped models
PEACECRAFT3_INSTALL=<dir> cargo test -p pcx-mdl -- --ignored   # pointed at the other build
```

The sweep asserts: the chunk walk consumes every byte exactly; `SEQS` and
`TEXS` sizes are whole multiples of their record strides; every `GEOS` chunk's
geoset walk lands on the chunk's final byte and every geoset opens with `VRTX`;
every model names itself; for every one of the **17,442** geosets of both builds,
the `MATS` framing — the trailer ends exactly on the next sub-tag,
`matrix_span_u32s == MATS.count`, `material_id < material count`, and
`unselectable <= 4`; and, for each of `TXAN` `RIBB` `PREM` `PRE2` `CAMS` `LITE`
`CLID`, the framing equalities above plus the per-field sanity checks
(`materialId` in range, `far > near`, ordered attenuation, `kind ∈ {0,1,2}`,
`PRE2`'s sub-chunk chain sorted by tag, `CLID`'s `header_size` equal to 96 plus
its node animation). It reports sequence, timeline and texture anomalies without
failing, because those are real properties of the shipped assets.

Result — 1.28c: **3,234 / 3,234 models, 8,672 meshes, 968,613 vertices, 819,287
triangles, 35,097 bones, 0 failures.** 1.29b: **3,249 / 3,249, 8,770 meshes,
978,194 vertices, 826,833 triangles, 35,257 bones, 0 failures.** The two builds
agree on every format claim in this note and disagree only on counts, which is
the expected shape of the difference.

## Where the Reforged PDBs fit

Blizzard's 2.0.1 symbols are present at `wc3/pdbs-2.0.1/` — 225 PDBs, 12 GB,
including Blizzard's own MDL tools and `Warcraft III.pdb` matching the local
Reforged install. They gave this work the names for fields that could otherwise
only be guessed: `MDLGENOBJECT` (`name`@0, `objectId`@80, `parentId`@84,
`flags`@88), `MDLBONESECTION` (`geosetId`, `geosetAnimId`,
`facialAnimationBoneIndex`), `MDLGEOSETSECTION` (`vertices`, `normals`,
`texCoords`, `primitives`, `materialId`), and `MDL::ReadBinBone` /
`ReadBinGeosets`.

Two of those were directly confirmatory. In-memory `MDLGENOBJECT` places
`parentId` at 84; the vanilla footman's on-disk bone record has `-1` at exactly
that offset shifted by the one leading `u32`. And the in-memory geoset's field
set matches the sub-block set found in the bytes.

**They are a hypothesis source, not an authority.** They describe 2.0.1, and
this project is 1.28c first. Every layout claim above is encoded from vanilla
bytes and enforced by the sweep; nothing was accepted from a PDB on trust. The
rule stands for the rest of this work: PDB supplies a name, the shipped files
decide the layout.

The geoset trailer is the clearest case of that rule working in both directions.
`MDLGEOSETSECTION` carried the *name* `materialId` for years before the field was
found on disk — and the PDB could not have supplied it, because it describes
Reforged's in-memory struct, not vanilla's `GEOS` bytes. The bytes supplied the
layout; the symbols then confirmed which offset the name belonged to.

## Appendix: how an install's version is determined

Not from the binaries. That sounds wrong until you look:

| File | Version resource |
|---|---|
| `wc3/game/app/game.dll` | 1.26 |
| `wc3/game/app/war3.exe` | 1.26 |
| `wc3/game/app/Storm.dll` | 1.0 |
| `Game.dll` inside `war3.mpq` | 1.0, and 4.3 MB smaller than the on-disk copy |

The on-disk `game.dll` is the retail disc's 1.26 launcher copy. The 1.28c game
code arrives inside the MPQs, not by patching the DLL, so neither the version
resource nor the file size identifies the build.

`pcx_mpq::Install::open` therefore fingerprints archive content instead: it hashes
an internal path from every member archive and matches against a table of
recorded digests. An unrecorded install reports `Version::Unknown` rather than
guessing.

This also uncovered the reason the table has to match per member:
`MpqSet::extract("(listfile)")` returns the first archive that holds the path,
which is `War3x.mpq` (299,575 bytes) and never `war3.mpq` (529,298 bytes),
because `War3Patch.mpq` has no listfile at all. The same trap that hid 3,737
textures would have hidden the fingerprint too.

framing that does not describe them would inflate the number without proving
anything. `EVTS` and `CLID` are counted separately again, because both measure a
node header — though `CLID`'s size also covers the node's animation, which is
what took the `eventnodes` count up when that chunk became a real parse.

The effect chunks are worth reading as a pair of columns rather than a total:
`PREM` and `LITE` are identical in both builds, `RIBB` and `TXAN` move in
opposite directions, and every framing equality above holds on **both** with zero
exceptions. The totals quoted in this note (715 ribbons, 1,300 cameras) are the
sum over the two builds because that is the set the sweep actually covers.

Differences that are **not** format differences and would have been fixed wrongly if
treated as one:

- **Archive capitalisation.** 1.28c spells them `war3.mpq` and `War3xlocal.mpq`; 1.29b
  spells them `War3.mpq` and `War3Local.mpq`. An exact-match priority list opens only one
  of five archives on the primary target. `MpqSet` now resolves names case-insensitively.
- **`Deprecated.mpq` is 1.29b only.** It holds content Blizzard removed from the live game
  but still ships, and it is the lowest-priority member.
- **`game.dll` does not exist in 1.29b.** Its game code is inside `Warcraft III.exe`. This
  does not affect any decoder here, but it means anything keyed on `game.dll` — including
  the RE workflow — has to resolve the right file per build.
- **The BLP palette is variable-length**, discovered only because 1.29b ships a ten-entry
  one. See `docs/re-notes/003-blp.md`.

## `MTLS` — materials

Also self-inclusive lengths, like `GEOS`: each record is a `u32` counting its
own four bytes, followed by that many bytes less four. The footman's three
records are 48, 76 and 120 bytes and tile the 244-byte chunk exactly.

Inside each record are `LAYS` sub-blocks — the texture layers. A layer is
`LAYS` + a layer index + its own declared length.

`MDLMATERIALSECTION` names the record fields `texLayers`, `priorityPlane`,
`materialFlags`, and `MDLTEXLAYER` names `shaderIdMDL`, `blendMode`, `flags`,
`textureId`, `flipKeys`, `transformId`, `coordId`, `alphaKeys`, `staticAlpha`,
`emissiveKeys`, `staticEmissive` and the fresnel set. Those are PDB field names
adopted after the framing had been measured, and only the framing is decoded.

**The layer body was unread for a while, and the reason is worth keeping.** The
first offset that looked like `textureId` turned out to be the layer's declared
length, and the second guess produced 1,784 layers pointing at a texture index the
model does not own across 1,784 separate models — a wrong-skeleton-shaped error
rather than an obvious break. It is decoded now, and what makes the reading
trustworthy is not a symbol but a bound: the sweep walks every layer of every
material — **6,959** layers on 1.28c, **7,057** on 1.29b — and asserts that each
one points at a texture the model actually ships.

### Texture binding is measured

```text
+0   "LAYS"
+4   u32  layer index
+8   u32  declared length — 28, or 100 when the layer animates
+12  u32  shaderId
+16  u32  blendMode
+20  u32  textureId          <- the one that matters
+24  u32  textureAnimId      (`NO_ID` when the layer has none)
+28  f32  staticAlpha        (1.0 when no `KMTA` track overrides it)
```

`textureId` sits at **LAYS+20**, and the Footman's three materials read 0, 1, 2
against the texture list `Footman.blp` / empty / `gutz.blp`. The value at
LAYS+8 is the declared layer length — 28, or 100 when the layer animates — and
reading *that* as a texture index produced materials pointing at textures 28 and
7. It looked plausible until the paths were checked, which is exactly the failure
mode this project's notes are for.

With `textureId` measured, `materialId` measured, and the trailer framing proved,
the whole chain from geoset to texture is now a matter of plumbing rather than
reading bytes. See *Geoset→material* above.

## Geoset→material — measured, not inferred

Status: **measured, proved, and applied.** The decoder reads `MATS` from its
count rather than from a tag scan, parses the trailer, carries the trailer's
fields on `Mesh`, and `to_bevy` binds each geoset to the material it names. The
measurement and the application are separable in principle; here they landed
together, and the offscreen capture is the evidence that the join actually shows
up on screen.

The material id is on disk. It is the first `u32` after the `MATS` body, and it
was being swallowed by the "scan to the next known tag" reader that decoded
`MATS`. No guessing is involved: the framing is proved by the chunk walk, the
field is named by Blizzard's own reader, and the values are checked against every
shipped model.

### It was never missing — it was attributed to `MATS`

Each `GEOS` entry is self-inclusive sized. The walk tiles its sub-blocks to the
byte for every model, so the framing is not in doubt; what was in doubt is where
`MATS` ended. Its body width cannot be derived from its count if the count is
read as "number of groups", so the reader scanned forward for the next known tag
and called everything in between `MATS`. That span was **not** all matrix
indices:

```text
MATS body                count*4 bytes      (matrix / node indices)
+0x00  u32     materialId
+0x04  u32     selectionGroup
+0x08  u32     unselectable                   (0, or 4)
+0x0c  f32     boundsRadius
+0x10  f32[3]  minimumExtent
+0x1c  f32[3]  maximumExtent
+0x28  u32     seqBoundsCount
+0x2c  28      each  { f32, f32[3], f32[3] }  <- the array starts here
--------------------------------------------------  44 fixed, then 28 * seqBoundsCount

then UVAS and its UVBS layers.
```

The Footman's geoset 0 carries 216 bytes of matrix indices and 408 bytes of
everything else; the old reader called all 624 bytes `MATS`. Two things fell out
immediately: `MATS` is in fact `count` u32s — exactly what its count means — and
because the trim to `sum(MTGC)` sits at the front of the span, the skinning
table's *length* was accidentally right even against a span four times too wide.
What was missing was the trailer's own name, and everything it carries.

### Byte offsets

Trailer offsets are relative to the end of the `MATS` body
(`geoset + off(MATS) + 8 + MATS.count*4`):

| offset | width | field |
|---|---|---|
| `+0x00` | `u32` | **materialId** |
| `+0x04` | `u32` | selectionGroup |
| `+0x08` | `u32` | unselectable (bit `0x4`) |
| `+0x0c` | `f32` | boundsRadius |
| `+0x10` | `f32[3]` | minimumExtent |
| `+0x1c` | `f32[3]` | maximumExtent |
| `+0x28` | `u32` | seqBoundsCount |
| `+0x2c` | `28` each | per-sequence bounds: `{ f32, f32[3], f32[3] } |

Seven words and then the count word, so the fixed part is **44 bytes** and the
array begins at `+0x2C`. Forty is the number an earlier draft of this section
used, and it desynchronises the walk by four bytes on every geoset in the set.

`seqBoundsCount` is **not** one record per sequence. It is either exactly the
sequence count or zero, with nothing in between and nothing over:
**5,971 exact / 2,701 none** on 1.28c (8,672 geosets) and **6,084 exact / 2,686
none** on 1.29b (8,770) — 17,442 geosets across the two builds and no third
value. Asserting `len == sequence_count` outright failed on 2,699 models, which
is how the real rule was found: the failures were dumped, every one of them read
zero, and the assertion became `count ∈ {0, sequence_count}`. On 1.28c that zero
case is 1,823 of 3,234 models, 1,525 of which ship no per-sequence bounds at
all. Where the count is non-zero it is exact — the Footman's 13 sequences give
13 records, its portrait's 5 give 5 — which is why the trailer's length varies
both within one chunk and between chunks.

### Evidence

**1. Blizzard's own binary reader, `World Editor.exe`.** The binary chunk reader
at RVA `0x687070` dispatches `'GEOS'` to `0x694010`, which calls the per-geoset
reader at `0x693db0`. After the sub-blocks it performs, with no tags and no
dispatch at all — just positional reads:

```
call 0x704030 (u32)   -> [edi + 0x94]      # first field after MATS
call 0x704030 (u32)   -> [edi + 0xc4]
call 0x704030 (u32)   -> [edi + 0xc8]
call 0x703e60 (f32)   -> [edi + 0xb0]
call 0x703e80 (3f32)  -> [edi + 0x98]
call 0x703e80 (3f32)  -> [edi + 0xa4]
call 0x691d10         -> seqBounds (+0xb4/+0xb8)
call 0x691e70         -> UVAS / UVBS
```

**2. The same struct offset is named `MaterialID` by the text reader.** The
`.mdl` keyword reader at `0x694370` resolves each geoset keyword through a jump
table (byte array at `0x69459c`, base = token id − 309) into a struct offset.
`MaterialID` is token 380 and its case is `mov [ebx + 0x94], eax` — the very
field the binary reader fills first. Neighbours confirm the layout:
`SelectionGroup` → `+0xc4`, `Unselectable` → `+0xc8 |= 4`, `BoundsRadius` →
`+0xb0`, `MinimumExtent` → `+0x98`, `MaximumExtent` → `+0xa4`.

**3. Both writers agree.** `World Editor.exe 0x694fd0` and `Warcraft III.exe
0x901a50` (with its seqBounds helper `0x8ffac0`) write `[+0x94]`, `[+0xc4]`,
`[+0xc8]`, `[+0xb0]`, `[+0x98]`, `[+0xa4]`, seqBounds, then `UVAS`. Two binaries,
same struct offsets, same order.

**4. The chunk walk proves the framing.** Reading `MATS` as `count` u32s and then
the **44-byte** fixed part plus `28 * seqBoundsCount` bytes lands exactly on
`UVAS` for **17,442 of 17,442 geosets** — 8,770 across 3,249 models on 1.29b and
8,672 across 3,234 on 1.28c — and the tag after the trailer is `UVAS` in every
single case. Zero exceptions. A wrong framing cannot land on a tag, and this is
the one claim here that can be falsified by a single number: with 40 in place of
the 44 the same walk lands on a valid tag for **0 of 8,672** geosets on 1.28c.

**5. The values are sane.** `materialId < material count` for every geoset of
both builds — 8,770 of 8,770 on 1.29b, never once out of range, with ids up to
56; on 1.28c, 8,672 of 8,672, the largest id 56 in a 57-material model
(`NightElf_Exp.mdx`), and no geoset anywhere sits in a model with no materials,
which is what makes the bound unconditional rather than guarded. `UVAS` count
equals the layer count of `material[materialId]` for 8,718 of them on 1.29b and
8,621 of 8,672 on 1.28c; the exceptions — 52 and 51 — are geosets with 2–3 UV
sets against one-layer materials (`CityCliffDoodad*`, `FreezingBreathTargetArt`,
`Volcano.mdx`), which is a quirk of `UVAS`, not of the mapping.

### What changed when it was applied

The decoder reads `MATS` from its count rather than from a tag scan, parses the
trailer, and carries on `Mesh`: `material_id`, `selection_group`,
`unselectable`, `bounds_radius`, `minimum_extent`, `maximum_extent` and
`seq_bounds`. `pcx-gfx`'s `to_bevy` binds `paths[material_id]`, and the offscreen
capture binds the same way, falling back to a flat colour when the named material
has no loadable texture rather than quietly borrowing another material's. Four
assertions hold with zero failures on 3,249 models today:

- the trailer lands on the next sub-tag — `UVAS` — for all 17,442 geosets of both
  builds;
- `matrix_span_u32s == MATS.count`;
- `material_id < material count` for every geoset, unconditionally;
- `unselectable <= 4`.

The assertion that used to pin the geoset and material counts *unequal* is gone.
It existed to stop a future change from quietly making them agree and burying the
question — which is the opposite of what should happen once the mapping itself is
read, so it went, and the inequality it guarded becomes a checked property per
mesh rather than a property of the model.

Also free once the trailer is parsed: `boundsRadius`, the extents and `seqBounds`
are the geoset's own bounds, which is the number the game culls with. The code
still measures a bounding box from vertices, which is close but not the same.

`selectionGroup` and `unselectable` are readable too; nothing derives from them
yet. The sweep sees only `0` and `4` — 8,470 and 202 on 1.28c, across 122 models,
mostly missiles, `CircleOfPower`, `EntangledGoldmine`, `FountainOfLifeBlood` and
the `TreeofLifeUpgrade` target art — and 21 of the 109 geosets in
`ArthasIllidanFight.mdx` carry non-zero selection groups (4 … 1301).

## `GEOA` — geoset animation

The chunk is a list of **self-inclusive** records — `len` counts its own four-byte
length field, so the data is `len - 4`. Each record is:

```text
+0   f32 static alpha
+4   u32 node flags
+8   f32 red
+12  f32 green
+16  f32 blue
+24  track header, 16 bytes:
       magic[4]  ("KGAA" alpha, "KGAC" colour, "KGAO" opacity)
       u32       key count
       u32       interpolation type (0 none, 1 linear, 2 hermite, 3 bezier)
       u32       global sequence id, or -1
+40  keys
```

A key is `{ frame: u32, value }`, and a tangented key appends an in and an out
tangent the same width as the value. So:

```text
key_len = 4 + components * 4          (no tangents)
key_len = 4 + components * 4 * 3     (hermite or bezier)
```

`components` is 1 for `KGAA`/`KGAO` and 3 for `KGAC`. `record_len - 4 == 24 +
Σ(16 + count * key_len)` holds for every shipped record, which is the invariant
the sweep enforces.

### Three mistakes that all looked plausible

**The key size was grouped wrong.** Written as `(4 + comp * 4) * 3` it gives 48
for a tangented colour key, where the truth is `4 + comp * 4 * 3` = 40 — the
frame is counted once, not three times. The four-byte-per-key difference was
enough to make colour tracks overrun their records while scalar ones still fit,
so most models passed.

**The track header was read as 12 bytes.** That left `0xFFFFFFFF` — actually the
global sequence id, meaning "none" — being read as a key frame, so tracks
produced frames of `0xFFFFFFFF` and values like `1e-41`. The count still matched,
so nothing complained.

**`len` was compared against instead of `len - 4`.** Because `len` counts its own
length field, every record looked like it had four bytes of unexplained padding.
That is what made me loosen the framing assertion to `<=` — and loosening it is
what let the misread header survive. Finding the off-by-four restored the strict
check, and the strict check is what makes the layout trustworthy.

## `TXAN` — texture animation

A run of records with **no node header and no name**: `u32 len`, then that
record's tracks. The record is nothing but its animation, which is why it cannot
be walked like `BONE`.

```text
+0   u32  len, counting its own four bytes
+4   "KTAT" / "KTAR" / "KTAS"    count interp globalSeq, then count keys
```

`MDLTEXANIMSECTION` in Blizzard's 2.0.1 symbols names the three arrays
`transkeys`, `rotkeys` and `scalekeys` and carries no alpha array — which is why
`KATF` appears in none of the shipped records. The magics and the order were
measured against vanilla bytes first; the symbol came second.

The invariant is exact and holds for all 279 records across both builds:

```text
len == 4 + Σ(16 + count * stride)
```

A concatenated-track reading satisfies the same sum with the size word honoured
only approximately, which is what makes the equality, not the total, the check.
The waterfall doodad pins it from the other direction: one 52-byte record, one
`KTAT` translation track, two 16-byte keys — `52 == 4 + 16 + 2 * 16`.

## `RIBB` — ribbons

A ribbon is a node, 52 bytes of emitter state, then its own tracks. The second
size word counts 96 *plus* the node's animation, so the state starts at
`+4 + node_size` and no fixed-stride walk is possible.

```text
 +0   u32  total size, counting its own four bytes
 +4   u32  node size: 96 + the node tracks that follow
 +8   char name[80]
 +88  u32  object id
 +92  i32  parent id
 +96  u32  flags
+100  node tracks (KGTR / KGRT), ending exactly at +4 + node_size

then 52 bytes of emitter state:
  +0   f32  height above the origin the ribbon is drawn at
  +4   f32  height below it
  +8   f32  alpha
  +12  f32  colour, three components
  +24  f32  edge lifetime, in seconds
  +28  u32  texture slot
  +32  u32  edges emitted per second
  +36  u32  texture rows
  +40  u32  texture columns
  +44  u32  material id
  +48  f32  gravity

then the emitter's own tracks: KRVS visibility, KRHA height above, KRHB height
below.
```

Both relations hold for all 715 records of both builds:

```text
node_size == 96 + Σ node tracks
total     == 4 + node_size + 52 + Σ own tracks
```

`textureSlot` reads 0 in all 715, so nothing is derived from it. The colour's
component order is not pinned by the bytes and is left as a plain triple.
`material_id` is checked against the model's own material count, the same way a
texture layer's `textureId` is.

## `PREM` — particle emitters (v1)

Same node framing as `RIBB`, different body: four floats, a fixed-width inline
particle path, then two more floats.

```text
 +0   u32  total size
 +4   u32  node size: 96 + the node tracks that follow
 +8   char name[80]
 +88  u32  object id
 +92  i32  parent id
 +96  u32  flags
+100  node tracks, ending exactly at +4 + node_size

then 284 bytes of emitter state:
  +0    f32 emission rate
  +4    f32 gravity
  +8    f32 longitude
  +12   f32 latitude
  +16   char particle path[260], padded to the full width
  +276  f32 life
  +280  f32 speed

then KPEV, the visibility track.
```

The path is a **fixed-width field**, not a NUL-terminated run: the walk over all
128 shipped records only lands on the following `KPEV` when the 260 bytes are
stepped over at once. `longitude` and `latitude` are emission-cone angles in
radians — across all 128 records they only ever take values such as π, π/2, π/6,
π/8 and π/10, which is what pins them. `MDLPARTICLE` names the three trailing
fields `path`, `life` and `speed`, in that order, which matches the measurement.

These are the v1 emitters, not the `PRE2` set; the two coexist in the shipped
models and a `PRE2` record is not a `PREM` record with a wider body. See
*`PRE2`* below.

## `CAMS` — cameras, and the reader that must not be shared

A camera is the one record in this format with **no node header at all**.

```text
+0    u32  total size, counting its own four bytes
+4    char name[80]
+84   f32  eye position, three components
+96   f32  field of view, in radians
+100  f32  far clip
+104  f32  near clip
+108  f32  target position, three components
+120  tracks: KCTR eye, KCRL roll, KTTR target
```

Two measurements decide fields that have no name of their own:

- **The clip pair is assigned by value, not by name.** In all 1,300 records of
  both builds the word at `+100` is strictly greater than the word at `+104`,
  which is only possible if the first is the far clip. `1300 / 1300`.
- **`field_of_view` is 0.7854 — π/4, a 45° cone — in 920 of the 1,300 records.**

The invariant is `size == 120 + Σ tracks`, exact for all 1,300 records.

### The gotcha worth keeping: `nodes()` must not be used for `CAMS`

`nodes()` is the shared `BONE`-shaped reader, and it *almost* works here. It puts
the name in the right place — for a camera the name really is at `+4` — and then
reads `objectId`, `parentId` and `flags` out of the eye position and the fov bit
pattern. Measured on the 656 camera records of 1.29b, all 656 of which the shared
reader walks without a single error:

| what `nodes()` returns | count |
|---|---|
| `parent_id` negative — really `eye.y`'s sign bit | 302 |
| `parent_id` in `0..100000` — looks exactly like a node index | 30 |
| `object_id` addressing a node the model actually ships | **0** |

Thirty records produce a parent id that is indistinguishable from a real node
index, which is the dangerous kind of wrong: nothing downstream can tell. A
pinned test asserts the misread so the shared reader cannot quietly come back
into use — the camera's own reader exists for this reason, and it is the reason
`CAMS` is not in the node-chunk sweep that counts `HELP` and `ATCH`.

## `LITE` — lights

Node framing like `RIBB`, with a 44-byte body instead of 52.

```text
 +0   u32  total size
 +4   u32  node size: 96 + the node tracks that follow
 +8   char name[80]
 +88  u32  object id
 +92  i32  parent id
 +96  u32  flags
+100  node tracks, ending exactly at +4 + node_size

then 44 bytes of light state:
  +0   u32  light kind
  +4   f32  attenuation start
  +8   f32  attenuation end
  +12  f32  colour, three components
  +24  f32  intensity
  +28  f32  ambient colour, three components
  +40  f32  ambient intensity

then the light's own tracks: KLAV visibility, KLAI intensity, KLAC colour,
KLBC ambient colour, KLBI ambient intensity.
```

The same two relations hold for all 500 records of both builds:

```text
node_size == 96 + Σ node tracks
total     == 4 + node_size + 44 + Σ own tracks
```

`kind ∈ {0, 1, 2}` and nothing else, across all 500 — so it is read as an enum
and an impossible value is a desynchronised walk rather than a fourth kind.
The distribution is 223 omnidirectional, 25 directional, 2 ambient per build,
identical on both. The attenuation pair is ordered in every record that has a
range at all, and the ambient colour is white in all 500.

`LITE` is the same trap as `CAMS`, and worse. `nodes()` reads the record's own
size as the size — which happens to be right — and then starts the name at `+4`,
but for a light the name is at `+8` and `+4` holds the **node** size word. So the
shared reader's name begins with the low byte of a size, and every field after it
is shifted by four. Measured on 1.29b, **0 of 250** records get their name, object
id or parent id right: the name comes back as a single `` ` `` (96, the bare
node size) and the object id as `0`. The reader must not be pointed at `LITE`.

## `PRE2` — particle emitters (v2)

`PRE2` is the newer of the two particle systems and by a wide margin the
commoner: **3,572** records on 1.28c and **3,628** on 1.29b, against `PREM`'s 64
per build. On 1.28c **1,091 models** carry this chunk against 29 for `PREM`, and
the two coexist inside individual models. It uses `RIBB`'s node framing, so it is
walked by the same shared reader; what follows the node is a fixed prelude and
then a chain of `KP2*` sub-chunks.

```text
  +0   u32  total size, counting its own four bytes
  +4   u32  node size: 96 + the node tracks that follow
  +8   char name[80]
  +88  u32  object id
  +92  i32  parent id
  +96  u32  flags
 +100  node tracks (KGTR / KGRT / KGSC), ending exactly at +4 + node_size

then, at +4 + node_size, 171 bytes of emitter prelude, unnamed — then:

  "KP2S" | "KP2L" | "KP2E" | "KP2V" | "KP2N" | "KP2W"
       u32  key count
       u32  lineType    (0 none, 1 linear, 3 bezier/hermite)
       u32  globalSeqId
   count * { u32 frame, f32 value [, f32 inTan, f32 outTan] }
```

A sub-chunk header is **the same 16 bytes an inline track uses**, and the same
`lineType` word decides the key stride — one `f32` per key, plus an in and an
out tangent when the interpolation asks for them. So `lineType` 3 keys are 16
bytes and `lineType` 0 or 1 keys are 8, and the chunk's size falls out of
`16 + count * stride` exactly as it does for a `KGTR`. All six tags decode
identically; nothing about them is special except where they may appear.

`lineType` only ever reads 0, 1 or 3 across the whole corpus — 2 never occurs —
and `globalSeqId` is `0xffffffff` ("none") in **9,527 of 9,533** sub-chunks.

### Three framing invariants, and the third is the strong one

```text
node_size == 96 + Σ node tracks
total     ==  4 + node_size + 171 + Σ sub-chunks
the sub-chunk chain is sorted by tag: KP2S < KP2L < KP2E < KP2V < KP2N < KP2W
```

All three hold on **7,200 / 7,200 records** across both builds — 3,572 on 1.28c,
3,628 on 1.29b — with no exceptions.

The third is the one worth keeping. It is not a byte count at all: it says the
chain is in one fixed tag order, so a reader that guessed a stride, or that
skipped a sub-chunk it had mis-measured, produces a chain that is either short
or out of order and fails even when the sizes happen to add up. And the order
is not a convention the reader chose — it is `Ord` on the tag enum, which is
what lets the sweep assert `windows(2).all(|w| w[0] <= w[1])` over the decoded
chain rather than over a hand-written list.

That invariant is only as good as the walk that produced the chain, so it was
checked against the bytes independently: no `KP2` byte sequence occurs anywhere
outside a walked sub-chunk boundary. A walk that had silently skipped a tag
could not then have found one here, which closes the gap between "the chain I
parsed is sorted" and "the chain in the file is sorted".

### What the tests pin

Three records, chosen so that no single one of them carries the whole argument.

**`Doodads\Underground\Plants\ShroomsBlue\ShroomsBlue.mdx`** — 271 bytes, one
record, and the smallest any build ships:

```text
+0x000  0f 01 00 00   total, 271
+0x004  60 00 00 00   node size, 96
+0x008  "BlizParticle08shockwaves", NUL-padded to 80
+0x058  04 00 00 00   object id 4
+0x05c  ff ff ff ff   parent id -1
+0x060  00 90 10 00   flags 0x00109000
+0x064  171 bytes and nothing else
```

Node size 96 admits no track, and the body runs to the end of the record, so
`271 = 4 + 96 + 171`. No `KP2*` tag appears anywhere in those 171 bytes, which
makes this the shortest possible demonstration that the prelude is 171 and not
168 or 174 — there is no chain to absorb the error. The prelude's first word,
`00 00 a0 c1`, is −20.0; it is read as a float only to pin the prelude's
*offset*, not as a named field.

**`Units\Creeps\InfernalCannonFlame\InfernalCannonFlame.mdx`** — 5,775 bytes, 13
records. Record 0 at `+0x000` is a single `KP2V`, count 8, `lineType` 0, whose
eight keys are frames 12400 / 16667 / 93333 / 96667 / 103333 / 103900 / 104367 /
106667 with values 0, 0, 0, 0, 0, 1, 0, 0 — a visibility track, and the shape
the commonest tag always has. Record 1 at `+0x1a3` carries an animated node
header (one `KGRT`, one key, 68 bytes, so node size 164) and a two-deep chain:

```text
body+171  KP2L  count 3  lineType 3  16 + 3*16 = 64
body+235  KP2E  count 5  lineType 0  16 + 5*8  = 56
```

`171 + 64 + 56 = 291`, the whole body. The two sizes differ only because
`lineType` 3 carries both tangents and 0 carries neither, which is the point:
the same header, the same stride rule, two different answers.

**`Abilities\Spells\Demon\DarkPortal\DarkPortalTarget.mdx`** pins the three
rarest tags on their own, because a reader that got their stride wrong could
hide behind the common ones. `KP2N` and `KP2W` appear in 141 records per build
and `KP2L` in 92. `DarkPortalTarget` carries `KP2V` (count 3, `lineType` 0, 40
bytes), then `KP2N` (count 4, `lineType` 3, 80), then `KP2W` (count 4,
`lineType` 3, 80) — `171 + 40 + 80 + 80 = 371`. `KP2N` and `KP2W` agree key for
key: frames 0, 1167, 1600, 2167 with values 120, 100, 40, 0. Two independent
sub-chunks carrying identical data is itself evidence that they are read the
same way and not accidentally transposed.

### The prelude is measured, not decoded

This is the deliberate gap. **171 bytes per record, every record, no
exceptions** — the width is as certain as anything else in this note, and it is
the width that the second invariant above turns on.

What those words *mean* is not decoded, and they are kept as raw bytes rather
than guessed into named floats. The Reforged PDB's `MDLPARTICLEEMITTER2` lists
40 plausible fields, and none of them was used: the PDB describes 2.0.1's
in-memory struct, and vanilla 1.28c bytes pin **widths, not names**. Naming
forty floats from a struct layout would produce something that compiles, looks
right in a hex dump and means nothing.

### Anomaly: keys opening on a negative frame

**22 sub-chunks** across both builds open on a negative frame — a `KP2E` at
−100 in `Hydralisk`, for instance. This is the same real phenomenon already
documented for camera tracks above, not a parsing error, and the sweep reports
it as an anomaly rather than failing on it: a track whose first frame is
negative is ordered-but-unusual, and lumping it in with "keys out of order"
would bury the 0 genuine ordering failures among 22 correct data.

### Cross-build difference: one ULP in a quaternion

In `InfernalCannonFlame`, the node `KGRT` quaternions round one ULP apart
between exporters — `0x3f32a26a` on 1.29b against `0x3f32a269` on 1.28c — which
is 30 bytes of the 5,775-byte chunk and the *only* difference between the builds
in the whole thing. The assertion on those values uses a tolerance; the frame
next to them is compared exactly, and everything framing-related is byte-exact
on both builds. Two exporters rounding the same rotation differently is a fact
about the exporters, not a discrepancy in the format.

## `CLID` — collision shapes

`CLID` is inline collision geometry after a node header. It has its own reader
because it is **not** `EVTS` with a different payload, and the reason is a
single word:

```text
+0   u32  header_size = 96 + Σ node-track bytes   <- NOT a constant 96
+4   char name[80]
+84  u32  object id
+88  i32  parent id
+92  u32  flags
+96  KGTR / KGRT / KGSC, occupying header_size - 96 bytes
     u32  kind        0 = box, 2 = sphere
     f32[3] * 2       box:   two corners,  24 bytes
     f32[3], f32      sphere: centre + 1,  16 bytes
```

`header_size` is the trap. The constant-96 rule holds for only **94%** of the
1,678 records: **96** of them carry a `KGTR` track inside the header, and
`Demoness` measures **152**. A reader that treated the header as always 96 would
read the kind word out of the middle of that track and then walk off the end of
the chunk — on the 6% of records that animate, and nowhere else, which is the
worst kind of failure this format offers.

Note that this is the *opposite* of `EVTS`, where the `KEVT` track trails the
measured header. The same sum written for an event object would be one track too
long here, which is why the node animation is not added again when the record's
size is computed.

### Framing

```text
header_size == 96 + Σ(node-track bytes)
Σ(header_size + 4 + geometry_len(kind)) == payload length
```

Both hold on every record of both builds: **846 / 846** on 1.28c and **832 /
832** on 1.29b — **1,678 records** across **1,004 models**. The second is the one
that matters — a geometry width one word wrong still parses, and leaves the chunk
looking plausible while every record after the first is misaligned, so the sum
is checked against the payload rather than trusted.

`flags` is `0x2000` in all **1,678** records — a bit that is set on a collision
shape and nothing else in the format, which is the first hint that the tag means
what it says. The kind word only ever reads **0 or 2**. Blizzard's
`MDLCOLLISIONSHAPE` union also names a cylinder and a plane, but no shipped
model carries one, so their widths would be guesses: anything other than 0 or 2
is refused with a typed error and never defaulted.

### The brief's premise was wrong, and the correction is the interesting part

The first reading of this chunk held that the Footman's `CLID` was **232 bytes
in one record**, with a leading count and 136 bytes of geometry after it.

It is **two records of 116** — `96 + 4 + 16`, twice. 232 = 116 × 2 exactly.
Once the record is sized from the kind word, the second record's header size
lands at offset `0xac`, which is where the sum says it must be.

So the floats previously reported as "a count and floats" were not: the leading
`u32 2` is the **kind** (sphere), not a count, and what looked like geometry was
sphere 1's centre plus its last word. Both claims were individually plausible
and jointly wrong, which is the failure mode this whole note is written against.

### The floats are returned raw, and that is a decision

The geometry floats are handed on in stored order, uncaptioned, and **no volume
is exposed**. A caller that wants a collision shape has to choose a reading of
its own and say so.

The evidence *for* the obvious reading is strong:

- every box is componentwise ordered, first vertex ≤ second, in all 255 of them;
- **241 / 255** boxes are symmetric about the origin in x and y, which is what a
  minimum/maximum pair around a centred model looks like;
- **78 / 237** multi-sphere models give every sphere in the model the same last
  word, which is the capsule idiom — a body swept by equal spheres — and no
  shipped sphere carries a non-positive one.

The evidence *against* over-claiming is what settled it:

- the cross-check against the model's own `MODL` extents **does not
  discriminate**. Only **531 / 591** spheres fit inside their own mesh's
  extents, and that is not an error — `CircleOfPower` legitimately exceeds the
  mesh it belongs to. A test built on this assumption fails for a correct
  reason, so it cannot be used as evidence.

So box-as-axis-aligned-bounds and sphere-as-centre-plus-radius stay
**hypotheses with corpus support, not proofs**. That is a deliberate line rather
than an unfinished section: a collision shape is a volume, a plausible-but-wrong
collision shape lets units walk through walls, and that is the worst thing this
decoder could get wrong. The width is proved and asserted; the meaning is not
claimed.

## Still open — semantics, not framing

**There is no chunk whose framing is undecoded.** Every tag in the format is
walked to the byte and every one of them is covered by at least one equality the
sweep enforces. What follows is the honest residue, and it is a list of
*meanings that were refused*, not of chunks still to crack:

| | what is proved | what is deliberately not decoded |
|---|---|---|
| `PRE2` prelude | 171 bytes, every record, measured several independent ways | the meaning of any of its ~40 words. Kept as raw bytes; no field is named |
| `CLID` geometry floats | the kind word, the two widths, and the store order | whether kind 0 is an axis-aligned box and kind 2 a sphere. Floats returned uncaptioned, no volume exposed |

Two smaller ones elsewhere in the file, listed so the list is complete rather
than flattering: `MODL`'s `+0x154` word (a radius or a scale — it sits below
the bounding diagonal in 1,487 of 1,492 non-zero cases, which is suggestive and
not decisive, and nothing derives from it) and `RIBB`'s colour component order
and `textureSlot` (0 in all 715 records, so nothing is derived from it either).

Everything here was refused on the same grounds: the bytes pin widths, not
names, and a guess that renders plausibly is worse than a documented gap. Where
a field is read but not interpreted, the note says which it is.

## Skinning

The chain from skeleton to screen, and what each step depends on:

| step | what |
|---|---|
| `sample_bone_pose` | a bone's tracks at one instant, evaluated independently |
| `Pose::then` | composes a child onto its parent — scale, rotate, translate |
| `bone_matrices` | world matrix per bone, walking the parent chain root-down |
| `skin_mesh` | each vertex's `GNDX` group, to that group's bone in `MATS` |

`parentId` addresses the whole node space, so `bone_matrices` takes a parent
resolver rather than scanning the bone list: a bone hanging from a helper must
resolve through the resolver, or the hierarchy silently collapses and every bone
reads as a root. The parent walk is iterative rather than recursive, and a cycle
in the chain truncates instead of recursing forever.

Composition keeps the pivot separate: a bone rotates about its own rest point, so
the pivot is subtracted from the vertex and added back into the matrix. Doing it
as a single offset makes a bone swing about the model origin instead of its joint.

Two of these were caught by tests that could not pass either way:

- A vector-valued track was returning the **midpoint** of its two keys for hermite
  interpolation, which is linear and not hermite. It looks almost right. The fix
  uses the in and out tangents; the key order is `frame, value, inTan, outTan`.
- A child-bone test asserted the parent's offset carried down while the synthetic
  parent had no pose at all, so identity was the correct answer. The test was
  wrong, not the code. The rewritten version gives the parent a real translation
  key and asserts parent + own offset, which is the property actually wanted.

Rotation keys interpolate as quaternions, not per component (2026-10-27).
`Linear` keys slerp; `Hermite` and `Bezier` keys use squad,
`slerp(slerp(q0, q1, t), slerp(outTan0, inTan1, t), 2t(1 - t))`, each slerp
along the shorter arc. The component-wise cubic left the unit sphere and folded
through zero where consecutive keys are stored with opposite signs.
`UI\Console\Orc\OrcUI-TimeIndicator.mdx` (`GeoSphere01`, 18 Hermite keys over the
60000 ms `Stand`) has such pairs: component-wise sampling put its sphere
edge-on at 10:00 game time, where the original client (Prologue02, 1280x960)
shows the day face. With quaternion sampling every sampled key is unit length and
the sphere turns monotonically. Squad through the stored tangents is a recreation
reading of the format; native tangent handling is not traced. Pinned by
`rotation_keys_interpolate_as_unit_quaternions` in `crates/pcx-mdl/tests/pose_sampling.rs`.

**`KEVT` is the only track in the format with a 4-byte key stride**, because it
carries frames and no values. Every other stride — 8 for a scalar, 16 for a
vector, 40 for a tangented colour — follows from having a value.

### The clip the viewer plays

Picking a clip by name is wrong for the Footman: its stand clips are
`Stand - 1`, `Stand - 2` and `Stand - 4`, never plain `Stand`, so an exact match
selects nothing. With nothing selected, `PlaybackState` is never inserted and the
animate system panics on a missing resource — a crash that looks unrelated to the
clip lookup.

The viewer now picks the clip whose window contains the model's first bone key,
which is the clip that demonstrably animates. The Footman resolves to
`Stand - 4` (7000..12267 ms), whose first key is at 7000 ms.
