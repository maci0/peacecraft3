# RE-000 — MPQ container (`Storm.dll`)

Status: **resolved** for reading. Implemented and tested in `crates/pcx-mpq`
(18 passing). Canonical statement of the format lives in `PLAN.md` §2.3; this file records
how it was established and what is still unexplained.

## What the shipped archives actually are

The four Complete Edition archives use the **classic MPQ v1 layout**. An early reading that
they "did not match the published layout" came from a brute-force sweep that used the wrong
keystream table and produced no plausible tables — a false negative that then blocked all
downstream work. Uncompressed, unencrypted blocks read back as valid `BLP1` headers at
exactly the offsets the block table names, which is the cheapest end-to-end proof that the
table positions are right.

## Method

1. `FUN_1501CFC0` (`ev_faddef74…`) — archive open. Read the header field accesses and the
   two table `CryptBlock` call sites out of the assembly.
2. `FUN_150175E0` (`ev_ddc2808a…`) — filename hash. Recovered the exact loop; confirmed by
   solving the on-disk table keys.
3. `FUN_15017570` (`ev_703ee25f…`) — table cipher. Recovered from assembly, then validated by
   a byte-for-byte comparison against Storm's own in-memory tables.
4. `FUN_15019B60` (`ev_e527eb69…`) — file open; established that the file key comes from the
   **basename** with table slice `0x300`.
5. `FUN_15017DC0` (`ev_494fd958…`) — sector read; established `file_key - 1` for the offset
   table and `file_key + i` per sector.

## Independent confirmation of the file key

The `(listfile)` sector offset table was decrypted **twice, by unrelated routes**:

- derived: `hash("(listfile)", 0x300)` = `0x2D2F0A94` → `FIX_KEY` → `0x47619FC7` → table key
  `0x47619FC6`;
- solved: a 256-candidate search (the key's low byte fixes `seed2` for the first dword, and
  the first offset must equal `(nsec+1)*4`) landed on `0x47619FC6` as the unique candidate,
  and that table is monotonic with its last entry equal to the block's compressed size.

## Runtime table discrepancy (RE-Q8)

The 1280-dword table read from a live Storm.dll process at `+0x4C2E4` differs from the fixed
table the archives use in **all 1280 words**. `FUN_15017650` is the builder and is called
lazily (`if (DAT_1504c2e4 == 0)`), which is consistent with the copy being populated at a
different time or from a different source than the one the data was encrypted with.
Recorded, unexplained, and not blocking: the reader never uses the runtime copy.

## Negative results worth keeping

- A 2³² sweep of table keys under the single-decrypt model found 10 538 weak candidates and
  nothing convincing. The model was wrong (wrong table), not the archives. Do not re-run it.
- The block cipher is **not** self-inverse: `seed2` folds in the *decrypted* word. There is a
  pinned test asserting this, to stop a future reader "simplifying" it back into an
  involution.
- Compression mask `0x12` is LZMA as an **exact value**. Testing it bitwise also matches
  plain zlib (`0x12 & 0x02`), which silently rejects most of the archive.

## Reader status against the shipped archives

`mpqxtract verify` over the 10,679 paths in `war3.mpq`'s `(listfile)`:

| outcome | count | note |
|---|---:|---|
| extract byte-identical to an independent implementation | 7,994 | 0 mismatches |
| explicit `Unsupported` | 2,685 | **all `.wav`** |

Every failure is ADPCM (`mask 0x41` = `0x40` mono + the ADPCM block header's low bit). The
independent reference reader fails identically — `Compression algorithm Huffman not
supported` — because it tests the Huffman bit first and `0x41` sets it. So this is a shared
gap in the format, not a defect in this reader. RE-Q10 stays open; the fix is the IMA/ADPCM
decoder, and it is **not** guessed at here: the exact step table and index-update schedule
must come from `Storm.dll`'s decompressor or from a verified reference before it ships.

Three MPQ rules that are easy to get wrong and cost most of the 7,994:

1. A sector offset table exists **only** when the block is compressed or encrypted. A plain
   stored block is consecutive fixed-size sectors. Reading a table where there is none is
   what made ~6,800 files fail at first.
2. A sector whose stored length equals the sector size (or exactly fills the output still
   owed) is **verbatim** and carries no compression-mask byte. Nearly incompressible files
   — the `.w3m` maps, `cs ≈ fs` — hit this on nearly every sector. Feeding that raw data to
   the imploder panics it.
3. The last synthetic offset of a stored block must be clamped to the packed length; `cs` is
   usually not a multiple of the sector size.

## Decompression dispatch (RE-Q10)

The entry point is `FUN_1500dd30` (`ev_7a8096c7364851125adccb976b2935d871216f7f449ab2145d69277e5f2ef313`),
called from `FUN_15017dc0`. Source file `SComp.cpp` (assertion at line `0x647`). Its exact
semantics, recovered from pseudocode:

```c
bVar1 = (byte)*src;                       // the sector's compression mask
n = 0;
n += (bVar1 & 0x08) ? 1 : 0;              // 0x08  implode
n += (bVar1 & 0x02) ? 1 : 0;              // 0x02  zlib
n += (bVar1 & 0x01) ? 1 : 0;              // 0x01  Huffman
n += ((char)bVar1 < 0)   ? 1 : 0;         // 0x80  ADPCM stereo
n += (bVar1 & 0x40) ? 1 : 0;              // 0x40  ADPCM mono
if (bVar1 & 0x34) return 0;               // 0x04 | 0x10 | 0x20 -> unsupported outright
```

Then it walks a `(mask, decoder)` table backwards, invoking every decoder whose mask is set,
ping-ponging between the destination, the source and a scratch buffer, and `memcpy`-ing the
final result back if it landed elsewhere.

Two consequences:

1. **The supported mask set is exactly `0x01 | 0x02 | 0x08 | 0x40 | 0x80`**, and
   `0x04`/`0x10`/`0x20` are hard-rejected. There is no bzip2, sparse, Huffman-only or LZMA
   path in this build — which is why `payload.rs` returning `Unsupported` for those is
   correct behaviour rather than a gap.
2. **Masks compose.** `0x41` is *Huffman then ADPCM*, two decoders in sequence — not
   "ADPCM with a stray bit", which is what this note previously assumed. So the 2,685 `.wav`
   entries need both a Huffman decoder and an ADPCM decoder, not one. That is the honest
   reason RE-Q10 is deferred rather than quickly finished.

Also measured:

- The canonical 89-entry IMA step table **is** in the binary at file offset `0x42AD8`
  (RVA `0x42248`), an exact byte match for `7, 8, 9, 10, … 32767`.
- REA xrefs to that address return nothing (`ev_788797af8de91bcf6ec5892cbc2a9c17d849e56c097104d9aa50c37e3aff4c77`),
  and the VA never appears as a 32-bit immediate anywhere in the image. The dispatch's own
  table symbol (`PTR_FUN_15042c88`) resolves to string data — Ghidra mislabelled it — so
  the table's real address must be recovered from the instruction stream, not from symbols.

Next step for whoever closes RE-Q10: read the table address out of `FUN_1500dd30`'s
instruction bytes, then decompile the entries whose masks are `0x40` and `0x01`.
