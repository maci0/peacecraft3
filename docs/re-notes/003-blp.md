# 003 — BLP1 textures

Status: **resolved on both builds.** All 6,273 `.blp` files the four 1.28c MPQs
contain decode to RGBA8, and the 1.29b set (6,696 files) is what falsified the one
assumption 1.28c could not — see *The palette is variable length* below.

## Header

Little-endian throughout. `BLP1` matches the published layout; the offsets were
confirmed against the shipped bytes before the decoder was written.

| Offset | Type | Meaning |
| --- | --- | --- |
| `0x00` | `char[4]` | `BLP0` / `BLP1` / `BLP2` |
| `0x04` | `u32` | content: `0` JPEG, `1` direct/palettised |
| `0x08` | `u32` | alpha bit depth (0, 1, 4, 8) |
| `0x0C` | `u32` | width |
| `0x10` | `u32` | height |
| `0x14` | `u32` | picture type (2, 3, 4 or 5 observed) |
| `0x18` | `u32` | has mipmaps |
| `0x1C` | `u32[16]` | mip offsets |
| `0x5C` | `u32[16]` | mip sizes |
| `0x9C` | `u32` | JPEG header size — only when `content == 0` |
| `0xA0` | | JPEG header bytes, then the palette |

BLP2 is the same shape with the flag region packed into bytes at `0x08`–`0x0B`
and the tables at `0x14` / `0x54`. No BLP2 file exists in 1.28c.

## The palette is variable length

The header table above says `0xA0` is followed by "the 256×4-byte BGRX palette",
and that is true of every 1.28c texture. It is **not** true of the format. The
palette occupies the space between its base (`0x9C`, or `0x94` on BLP2) and
`mip_offsets[0]` — whatever is there — and not a fixed 1024 bytes:

```text
palette_entry_count = (mip_offsets[0] - base) / 4      // BLP2: base = 0x94
```

`Editor-Toolbar-MapValidation.blp`, in the 1.29b legacy build, is 878 bytes with a
16×16 image and a **ten-entry** palette; its mip offsets reach only `8`, so the
palette genuinely ends there and the mip data starts immediately after. Reading a
fixed 1024 bytes fails that file as *truncated* — which is the useful failure, but
it arrives as a size error rather than as a framing error, so it reads like a
corrupt file instead of like a wrong layout.

This is the clearest example in the project of a cross-check earning its keep. The
assumption was not sloppy; it was **never contradicted**, because every 1.28c
texture carries a full 256-entry palette. Only sweeping the other build found it.
A decoder that passed on one build could still be wrong about the format.

A decoded palette always reports 256 entries, with the absent ones zero, so a
short palette is indistinguishable from one whose tail is transparent black.
`palette_entry_count` is what tells the two apart, and callers that care about the
difference have to ask for it.

## Mip chain

Mip `n` is `mip_size[n]` bytes at `mip_offset[n]`, and each level halves both
dimensions down to 1×1. Across all 6,273 shipped textures:

* `offset[n] + size[n] == offset[n + 1]` for every level but the last,
* `offset[last] + size[last] == file length`.

These are asserted in `shipped_textures_have_a_coherent_mip_chain` rather than
assumed, which is what made the layout trustworthy before any pixel work.

## Direct content (`content == 1`)

1,349 files. Every one is uncompressed and comes in exactly two shapes:

| Size | Layout |
| --- | --- |
| `w * h` | index plane only, alpha opaque |
| `w * h * 2` | index plane, then a separate alpha plane |

Both planes are **planar, not interleaved**. `SelectionCircleLarge.blp` settles
it: its first 16,384 bytes hold a single distinct value (palette index 0) while
the next 16,384 hold 83 distinct values. Under an interleaved reading both
halves would be identical mixtures, which they are not.

Distribution: type 3 → 254 `2×`, type 4 → 781 `2×`, type 5 → 297 `1×` and 17
`2×`. Type 2 appears only with `content == 0`.

## JPEG content (`content == 0`)

4,924 files — the bulk of the set, including every loading screen.

Mip payloads are **not** standalone JPEGs. The file carries one shared header
of `jpeg_header_size` bytes at `0xA0`, and that header stops part-way through
the frame: in `WarcraftIIIFTLogo.blp` it ends on `ff c0`, the start of `SOF0`,
and the mip bytes resume with that marker's length and body. So

```
stream = jpeg_header ++ mip_bytes
```

is the JPEG, and neither half is valid alone. `blpx dump` confirms this: no mip
contains `ff d8`.

These are four-component Adobe JPEGs: `jpeg-decoder` reports `CMYK32` for every
decoded mip (39,927 mips), but see below for how the components are read.

### Component conversion

The four components are inverted BGRA, not CMYK ink, whatever `alpha_bits` says:

```
R = 255 - c2      G = 255 - c1      B = 255 - c0      A = 255 - c3
```

`(40, 66, 67, 0)` → `(188, 189, 215, 255)`, which matches an independent decoder
on loading screens, whose fourth component is `0`. That sample cannot separate
alpha from black ink. Two `alpha_bits 0` textures do:

- `Textures\Base.blp`: fourth component `0` at mip 0 and `255` at mips 1-8. Read
  as ink, every lower mip decoded solid black and minified building foundations
  rendered black; the original client (Prologue02, 1280x960) draws them in the
  mip-0 wood colors. Its Great Hall material is filter mode 0, so alpha is unused.
- `UI\Glues\Loading\Backgrounds\Campaigns\HumanSymbol.blp`: fourth component
  `255` at the corners and `0` on the emblem. `LordaeronBackground.mdx` draws it
  with filter mode 2 (blend), and the original Human01 loading screen shows the
  emblem cut out over the parchment. Ink or an ignored fourth component would both
  leave opaque black corners.

Pinned by `four_components_are_inverted_bgra`.

#### Census of the change

`crates/pcx-blp/tests/jpeg_fourth_component_census.rs` (ignored; run with
`PEACECRAFT3_LEGACY_DIR` set) decodes every mip of every JPEG-content BLP that
`MpqSet::open_wc3` resolves in the Legacy 1.29.2.9231 install (`War3.mpq`,
`War3x.mpq`, `War3Local.mpq`, `War3xLocal.mpq`, highest-priority copy per path;
shadowed copies are not counted). Result on 2026-10-27:

- 6,696 BLPs extracted, 5,318 JPEG content, 0 undecodable mips. All 5,318 decode
  as four-component.
- `alpha_bits > 0`: 1,275 files, unchanged by the rule.
- `alpha_bits == 0`: 4,043 files. In 3,574 the fourth component is `0` in every
  mip, so the old and new readings agree. In 469 it is non-zero in at least one
  mip, and those are the files the change affects.
- Of the 469: 466 are non-zero at mip 0; 3 only at mips 1 and below
  (`Textures\Base.blp`, `Doodads\Cinematic\ThrallsHut\Base.blp`,
  `Units\Critters\ElfVillagerWoman\ElfVillagerWoman.blp`); 465 are non-zero at
  every mip.
- Files with a non-zero fourth component, by mip index 0 to 9: 466, 468, 468,
  468, 468, 214, 131, 104, 79, 10.
- Fourth-component range over all mips: `(0, 255)` in 442 of the 469; the other 27
  have other ranges.
- By path: 279 under `UI\Glues\` (225 `SinglePlayer\Undead3D_Exp`, 11 `Loading\Backgrounds`, the rest other `SinglePlayer` sets), 188 under `Doodads\Cinematic\`, 1 under `Units\Critters\`, plus `Textures\Base.blp`.

These 469 files now carry their fourth component as alpha. `Textures\Base.blp`
and `HumanSymbol.blp` were checked against original-client captures (no recreation
capture of that loading screen exists yet); the others were
not, and a material that blends one of them now shows its authored alpha.
